Meeting Transcription & Summarization

Architecture Overview

How It Works

Platform Infrastructure

The entire solution runs on Nutanix AHV, a secure enterprise-grade hypervisor that provides the virtualization layer for all compute, storage, and networking. On top of AHV, NKP (Nutanix Kubernetes Platform) provisions and manages the Kubernetes environment, providing container orchestration, auto-scaling, service discovery, and lifecycle management for all application workloads.

Kubernetes Workloads (db-project-003 namespace)

All use-case components are deployed as pods within the db-project-003 Kubernetes namespace:

  • Portal UI — A lightweight static front-end (HTML, CSS, JavaScript) that provides the meeting transcript upload interface, architecture visualization, and summary results display. Served by a Python-based development server that also acts as the API proxy.
  • API Proxy (server.py) — A server-side CORS proxy that routes browser requests to the Nutanix AI endpoints. Because the NAI inference service does not return browser CORS headers, all /api/ai/* requests are forwarded server-side with the bearer token injected, eliminating cross-origin restrictions.
  • PostgreSQL 16 (pg-db) — A relational database that stores meeting metadata, summary results, audit logs, and user activity. Exposed internally via ClusterIP on port 5432. Data is persisted on a Nutanix Volumes PVC (20 GiB) to ensure durability across pod restarts and rescheduling.
  • ChromaDB (ch-db) — An open-source vector database used as the RAG (Retrieval-Augmented Generation) store for transcript embeddings. Meeting transcript segments are vectorized using the NAI embedding model and stored in ChromaDB for fast similarity search. Exposed internally via ClusterIP on port 8000 with its own Nutanix Volumes PVC (20 GiB).
  • Ingress / LoadBalancer Service — External traffic is routed into the cluster via a Kubernetes LoadBalancer service, providing a stable IP address for browser access without requiring DNS configuration.

AI & Inference (Nutanix AI — NAI)

Nutanix AI (NAI) provides the enterprise inference endpoints that power the meeting summarization:

  • Chat Completions (llama3-1-8b) — The primary LLM endpoint. When a transcript is uploaded or pasted, the full text is sent along with a structured system prompt that instructs the model to return a JSON object containing the meeting title, type, date, duration, participants, executive summary, key points, action items, decisions made, follow-ups, and matter references. The model performs legal meeting analysis to extract actionable intelligence.
  • Embeddings (llama-3-2-embed) — The embedding model vectorizes transcript segments and user queries into high-dimensional vectors. These vectors are stored in ChromaDB and used for semantic search—enabling the RAG pipeline to retrieve the most relevant transcript passages when performing contextual analysis.

RAG Pipeline for Transcript Analysis

The Retrieval-Augmented Generation pipeline works as follows:

  1. Transcript Ingestion — The user uploads a transcript file (TXT, PDF, DOCX) or pastes transcript text. The browser extracts text using FileReader (TXT), mammoth.js (DOCX), or pdf.js (PDF).
  2. Query Embedding — Transcript segments are sent to the NAI embedding endpoint (llama-3-2-embed), which returns vector representations.
  3. Vector Search — Embedding vectors are queried against ChromaDB's transcript collection to find semantically similar passages for context.
  4. Context Assembly — Retrieved passages and meeting metadata are assembled as context for the LLM.
  5. LLM Summarization — The transcript text, retrieved context, and system prompt are sent to the NAI chat completions endpoint (llama3-1-8b), which produces the structured meeting summary with action items, decisions, and follow-ups.

Storage Layer

  • Nutanix Unified Storage — Serves as the model repository for NAI, hosting the LLM weights, tokenizer configurations, and model artifacts for both the chat completions model (llama3-1-8b) and the embedding model (llama-3-2-embed). This ensures model data resides on-prem with enterprise-grade data protection, deduplication, and replication.
  • Nutanix Volumes — Provides persistent block storage for the Kubernetes PVCs backing PostgreSQL and ChromaDB. Volumes ensures data durability, snapshots, and consistent performance for database workloads running as containerized pods on NKP.

Data Flow Summary

  1. User uploads a meeting transcript (TXT, PDF, DOCX) or pastes transcript text via the Portal UI.
  2. The browser extracts the text content and sends it to the API Proxy along with the selected meeting type.
  3. The API Proxy forwards the request (with authentication) to the NAI chat completions endpoint.
  4. NAI analyzes the transcript and returns a structured JSON response with summary, action items, decisions, key points, and follow-ups.
  5. The Portal UI renders the results: meeting overview, executive summary, action items with assignees and deadlines, decisions made, key discussion points, and follow-up timeline.
  6. Meeting metadata is saved to PostgreSQL for audit and history tracking.
  7. Transcript embeddings are stored in ChromaDB for future RAG-powered search and analysis.
