Legal Intake & Triage

Architecture Overview

How It Works

Platform Infrastructure

The entire solution runs on Nutanix AHV, a secure enterprise-grade hypervisor that provides the virtualization layer for all compute, storage, and networking. On top of AHV, NKP (Nutanix Kubernetes Platform) provisions and manages the Kubernetes environment, providing container orchestration, auto-scaling, service discovery, and lifecycle management for all application workloads.

Kubernetes Workloads (ntnx-use-cases namespace)

All use-case components are deployed as pods within the ntnx-use-cases Kubernetes namespace:

  • Portal UI — A lightweight static front-end (HTML, CSS, JavaScript) that provides the intake form, architecture visualization, and triage results display. Served by a Python-based development server that also acts as the API proxy.
  • API Proxy (server.py) — A server-side CORS proxy that routes browser requests to the Nutanix AI endpoints. All /api/ai/* requests are forwarded server-side with the bearer token injected, eliminating cross-origin restrictions.
  • PostgreSQL (pg-db) — A relational database that stores intake metadata, triage results, audit logs, and user activity. Exposed internally via ClusterIP on port 5432. Data is persisted on a Nutanix Volumes PVC to ensure durability across pod restarts.
  • ChromaDB (ch-db) — An open-source vector database used as the RAG store for matter embeddings. Intake descriptions are vectorized using the NAI embedding model and stored in ChromaDB for fast similarity search to find similar past matters. Exposed internally via ClusterIP on port 8000 with its own Nutanix Volumes PVC.
  • Ingress / LoadBalancer Service — External traffic is routed into the cluster via a Kubernetes LoadBalancer service, providing a stable IP address for browser access.

AI & Inference (Nutanix AI — NAI)

Nutanix AI (NAI) provides the enterprise inference endpoints that power the intake triage:

  • Chat Completions (llama3-1-8b) — The primary LLM endpoint for triage classification. When an intake request is submitted, the description, urgency, and practice area are sent with a structured system prompt. The model returns JSON containing matter type, jurisdiction, urgency assessment, risk level, routing recommendation, estimated response time, similar matters, and next steps.
  • Embeddings (llama-3-2-embed) — The embedding model vectorizes intake descriptions into high-dimensional vectors. These vectors are stored in ChromaDB and used for semantic search—enabling the RAG pipeline to retrieve the most relevant similar matters from the firm's historical intake database.

RAG Pipeline for Intake Matching

The Retrieval-Augmented Generation pipeline for intake triage works as follows:

  1. Intake Embedding — The user's matter description is sent to the NAI embedding endpoint (llama-3-2-embed), which returns a vector representation.
  2. Vector Search — The embedding vector is queried against ChromaDB's matter collection to find the most semantically similar past intakes.
  3. Context Assembly — Retrieved similar matters (titles, outcomes, similarity scores) are assembled as context for the LLM.
  4. LLM Triage — The intake details, retrieved context, and system prompt are sent to the NAI chat completions endpoint (llama3-1-8b), which produces the final triage with matter type, urgency, risk, routing, and recommended next steps.

Storage Layer

  • Nutanix Unified Storage — Serves as the model repository for NAI, hosting the LLM weights and configurations for both the chat completions model (llama3-1-8b) and the embedding model (llama-3-2-embed). This ensures model data resides on-prem with enterprise-grade data protection.
  • Nutanix Volumes — Provides persistent block storage for the Kubernetes PVCs backing PostgreSQL and ChromaDB. Volumes ensures data durability, snapshots, and consistent performance for database workloads running on NKP.

Data Flow Summary

  1. User submits an intake request via the Portal UI (requestor, department, matter description, urgency, practice area).
  2. The browser sends the form data to the API Proxy.
  3. The API Proxy forwards the request (with authentication) to the NAI chat completions endpoint; optionally, the matter description is embedded and queried against ChromaDB for similar matters.
  4. NAI returns a structured JSON response with matter type, jurisdiction, urgency, risk, routing, timeline, similar matters, and next steps.
  5. The Portal UI renders the triage results: matter type badge, urgency/risk indicators, routing card, timeline, similar matters list, and next steps.
  6. Intake metadata is saved to PostgreSQL for audit and history tracking.
