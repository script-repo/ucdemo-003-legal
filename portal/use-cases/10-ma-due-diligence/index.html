M&A Due Diligence

What This Does

M&A Due Diligence extracts key clauses from deal document sets — including change-of-control provisions, assignment restrictions, and consent requirements — and generates structured diligence reports and issues lists. Instead of deal teams spending weeks manually reviewing data rooms, the AI identifies material terms, assesses risk, and produces a client-ready summary in minutes.

Upload contracts, LOIs, material agreements, or any deal-related documents. The AI extracts parties, key clauses (change-of-control, assignment, consent, indemnification, termination, IP), flags risks, and builds an issues list with severity ratings and recommendations — reducing deal timeline and improving consistency across deals.

Data Flow Summary

  1. User uploads deal documents (TXT, PDF, DOCX) or pastes document text via the Portal UI.
  2. The browser extracts the text content and sends it to the API Proxy.
  3. The API Proxy forwards the request (with authentication) to the NAI chat completions endpoint.
  4. NAI analyzes the documents and returns a structured JSON response with risk scores, key terms, issues, and parties.
  5. The Portal UI renders the results: risk score badge, summary, extracted clauses table, issues list, and parties.
  6. Analysis metadata is saved to PostgreSQL for audit and history tracking.
  7. Clause embeddings are stored in ChromaDB for future RAG-powered comparative analysis.

Architecture Overview

How It Works

Platform Infrastructure

The entire solution runs on Nutanix AHV, a secure enterprise-grade hypervisor that provides the virtualization layer for all compute, storage, and networking. On top of AHV, NKP (Nutanix Kubernetes Platform) provisions and manages the Kubernetes environment, providing container orchestration, auto-scaling, service discovery, and lifecycle management for all application workloads.

Kubernetes Workloads (db-project-003 namespace)

All use-case components are deployed as pods within the db-project-003 Kubernetes namespace:

  • Portal UI — A lightweight static front-end (HTML, CSS, JavaScript) that provides the document upload interface for M&A due diligence, architecture visualization, and analysis results display. Served by a Python-based development server that also acts as the API proxy.
  • API Proxy (server.py) — A server-side CORS proxy that routes browser requests to the Nutanix AI endpoints. Because the NAI inference service does not return browser CORS headers, all /api/ai/* requests are forwarded server-side with the bearer token injected, eliminating cross-origin restrictions.
  • PostgreSQL 16 (pg-db) — A relational database that stores deal metadata, analysis results, audit logs, and user activity. Exposed internally via ClusterIP on port 5432. Data is persisted on a Nutanix Volumes PVC (20 GiB) to ensure durability across pod restarts and rescheduling.
  • ChromaDB (ch-db) — An open-source vector database used as the RAG (Retrieval-Augmented Generation) store for clause embeddings. Deal clauses are vectorized using the NAI embedding model and stored in ChromaDB for fast similarity search. Exposed internally via ClusterIP on port 8000 with its own Nutanix Volumes PVC (20 GiB).
  • Ingress / LoadBalancer Service — External traffic is routed into the cluster via a Kubernetes LoadBalancer service, providing a stable IP address for browser access without requiring DNS configuration.

AI & Inference (Nutanix AI — NAI)

Nutanix AI (NAI) provides the enterprise inference endpoints that power the M&A due diligence analysis:

  • Chat Completions (llama3-1-8b) — The primary LLM endpoint. When deal documents are uploaded, the text is sent along with a structured system prompt that instructs the model to return a JSON object containing the risk score, risk level, summary, key terms (change-of-control, assignment, consent, indemnification, termination, IP), issues list with severity, and parties. The model performs legal reasoning to identify material clauses, assess risk, and generate actionable recommendations.
  • Embeddings (llama-3-2-embed) — The embedding model vectorizes deal clauses and user queries into high-dimensional vectors. These vectors are stored in ChromaDB and used for semantic search—enabling the RAG pipeline to retrieve the most relevant clauses from the firm's clause library when performing comparative analysis.

RAG Pipeline

The Retrieval-Augmented Generation pipeline works as follows:

  1. Query Embedding — The user's document text is sent to the NAI embedding endpoint (llama-3-2-embed), which returns a vector representation.
  2. Vector Search — The embedding vector is queried against ChromaDB's contract_clauses collection to find the most semantically similar clauses from the firm's existing playbook and precedent library.
  3. Context Assembly — Retrieved clauses and their metadata (section references, risk ratings, standard language) are assembled as context for the LLM.
  4. LLM Analysis — The document text, retrieved context, and system prompt are sent to the NAI chat completions endpoint (llama3-1-8b), which produces the final analysis with risk scoring, clause extraction, and issues identification.

Storage Layer

  • Nutanix Unified Storage — Serves as the model repository for NAI, hosting the LLM weights, tokenizer configurations, and model artifacts for both the chat completions model (llama3-1-8b) and the embedding model (llama-3-2-embed). This ensures model data resides on-prem with enterprise-grade data protection, deduplication, and replication.
  • Nutanix Volumes — Provides persistent block storage for the Kubernetes PVCs backing PostgreSQL and ChromaDB. Volumes ensures data durability, snapshots, and consistent performance for database workloads running as containerized pods on NKP.
