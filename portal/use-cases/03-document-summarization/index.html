Document Summarization

What This Does

Document Summarization takes a legal document — a contract, brief, memorandum, or filing — and produces a structured, AI-generated summary in seconds. Instead of reading dozens of pages to extract the key points, an attorney uploads or pastes the document, selects a detail level (brief, standard, or detailed), and receives an organized breakdown with the document title, type, executive summary, key facts, parties, dates, obligations, and a section-by-section analysis.

The summary is generated by an on-premises LLM running on Nutanix AI, ensuring that sensitive legal documents never leave the firm's infrastructure. Results are saved for future reference, so previously summarized documents can be recalled instantly without re-processing.

Data Flow Summary

  1. User uploads a document (TXT, PDF, DOCX) or pastes text via the Portal UI, and selects a summary length (brief, standard, or detailed).
  2. The browser extracts the text content and sends it to the API Proxy.
  3. The API Proxy forwards the request (with authentication) to the NAI chat completions endpoint.
  4. NAI summarizes the document and returns a structured JSON response with title, document type, executive summary, key facts, section breakdown, and word counts.
  5. The Portal UI renders the results: title card, executive summary, key facts as tags, section-by-section breakdown, and word count comparison.
  6. Summary metadata is saved to PostgreSQL for audit and history tracking.
  7. Document embeddings are stored in ChromaDB for future RAG-powered summarization of long documents.

Architecture Overview

How It Works

Platform Infrastructure

The entire solution runs on Nutanix AHV, a secure enterprise-grade hypervisor that provides the virtualization layer for all compute, storage, and networking. On top of AHV, NKP (Nutanix Kubernetes Platform) provisions and manages the Kubernetes environment, providing container orchestration, auto-scaling, service discovery, and lifecycle management for all application workloads.

Kubernetes Workloads (ntnx-use-cases namespace)

All use-case components are deployed as pods within the ntnx-use-cases Kubernetes namespace:

  • Portal UI — A lightweight static front-end (HTML, CSS, JavaScript) that provides the document upload interface, text paste area, summary length selector, architecture visualization, and structured summary results display. Served by a Python-based development server that also acts as the API proxy.
  • API Proxy (server.py) — A server-side CORS proxy that routes browser requests to the Nutanix AI endpoints. Because the NAI inference service does not return browser CORS headers, all /api/ai/* requests are forwarded server-side with the bearer token injected, eliminating cross-origin restrictions.
  • PostgreSQL 16 (pg-db) — A relational database that stores summary history, document metadata, audit logs, and user activity. Exposed internally via ClusterIP on port 5432. Data is persisted on a Nutanix Volumes PVC (20 GiB) to ensure durability across pod restarts and rescheduling.
  • ChromaDB (ch-db) — An open-source vector database used as the RAG (Retrieval-Augmented Generation) store for document embeddings. Document chunks are vectorized using the NAI embedding model and stored in ChromaDB for fast similarity search during summarization. Exposed internally via ClusterIP on port 8000 with its own Nutanix Volumes PVC (20 GiB).
  • Ingress / LoadBalancer Service — External traffic is routed into the cluster via a Kubernetes LoadBalancer service, providing a stable IP address for browser access without requiring DNS configuration.

AI & Inference (Nutanix AI — NAI)

Nutanix AI (NAI) provides the enterprise inference endpoints that power document summarization:

  • Chat Completions (llama3-1-8b) — The primary LLM endpoint. When a document is uploaded or pasted, the full text is sent along with a structured system prompt that instructs the model to return a JSON object containing the document title, type, executive summary, key facts (dates, parties, issues, terms, obligations), section-by-section breakdown, and word counts. The user selects a detail level (brief, standard, or detailed) to control summary length.
  • Embeddings (llama-3-2-embed) — The embedding model vectorizes document chunks and user queries into high-dimensional vectors. These vectors are stored in ChromaDB and used for semantic search—enabling the RAG pipeline to retrieve the most relevant context when generating summaries for long documents.

RAG Pipeline for Summarization

The Retrieval-Augmented Generation pipeline for document summarization works as follows:

  1. Document Ingestion — The user uploads a document (TXT, PDF, DOCX) or pastes text. The browser extracts text using FileReader (TXT), mammoth.js (DOCX), or pdf.js (PDF).
  2. Chunk Embedding — For long documents, chunks are sent to the NAI embedding endpoint (llama-3-2-embed), which returns vector representations stored in ChromaDB.
  3. Vector Search — When summarization is requested, relevant chunks are retrieved from ChromaDB via semantic search to provide context.
  4. Context Assembly — Retrieved chunks and document metadata are assembled as context for the LLM.
  5. LLM Summarization — The document text (or retrieved context), user-selected detail level, and system prompt are sent to the NAI chat completions endpoint (llama3-1-8b), which produces the structured summary with executive summary, key facts, and section breakdown.

Storage Layer

  • Nutanix Unified Storage — Serves as the model repository for NAI, hosting the LLM weights, tokenizer configurations, and model artifacts for both the chat completions model (llama3-1-8b) and the embedding model (llama-3-2-embed). This ensures model data resides on-prem with enterprise-grade data protection, deduplication, and replication.
  • Nutanix Volumes — Provides persistent block storage for the Kubernetes PVCs backing PostgreSQL and ChromaDB. Volumes ensures data durability, snapshots, and consistent performance for database workloads running as containerized pods on NKP.
